## Evaluation of Performance and Technical Behaviour

Looking back at the development of **Shen_ren.indie.music**, the project became much more technically connected than I expected at the beginning. My original plan was closer to a visually designed community website for indie music listeners, but the final prototype developed into a database-driven web application with several connected systems: a homepage carousel, recommendation rows, a Browse page with filters, location-based recommendations, user profile display, room detail pages, and a basic comment function. Because of this, the main performance question was not only whether the pages loaded, but whether the different parts of the system behaved reliably when they interacted with each other.

One of the strongest parts of the final prototype is that the Sound Room content is mostly driven by the SQLite database rather than being manually repeated in HTML. The homepage hero carousel pulls room data from the database, and the recommendation rows use tags such as `chill`, `late-night`, `indie`, and `sydney` to display different groups of rooms. The Browse page also uses query parameters to filter rooms by genre, mood, and location. This made the application more maintainable, because the same room records could appear across the homepage, Browse page, and individual room detail pages. Instead of treating each page as a separate static design, the final system has a clearer relationship between data, routes, and interface.

However, using dynamic data also exposed several technical weaknesses. At one point, the homepage carousel displayed undefined values because the frontend JavaScript expected different field names from the database. The script was originally reading values such as `name` or `online`, while the database query returned `title`, `member_count`, `comment_count`, and `cover_image`. The problem was not that the SQL query failed, but that the frontend and backend did not agree on the shape of the data. Fixing this made me understand that a dynamic interface depends on consistent data mapping. When the controller, template, and JavaScript use different names for the same thing, the application may still run, but the user experience breaks.

The carousel also showed how small JavaScript decisions can affect perceived performance. Initially, the homepage loaded correctly, but after clicking the left or right arrow, the information box under the carousel sometimes disappeared. After testing, I found that this was related to the carousel script being loaded more than once, and also to the `is-changing` animation state not always being safely removed if rendering failed. I improved this by loading `soundroom-carousel.js` only once, adding checks for missing elements such as `roomCounter`, and making the render process safer. This was an important lesson because the issue was not visible on first page load; it only appeared through interaction. A page can appear functional at first but still perform poorly when users actually use it.

The location recommendation feature was another useful technical test. I used an API-style location detection process so the homepage could recommend local rooms. At first, the detected location was Waterloo, but the database did not have a `waterloo` tag. It had `sydney`. This meant the system returned no rooms even though Sydney rooms existed. I solved this by normalising suburbs such as Waterloo, Redfern, Mascot, and Newtown into the broader `sydney` tag. Later, I realised that the database location tags were not only real cities. They also included tags such as `berlin`, `hong-kong`, `tokyo`, `new-york`, `bedroom`, `studio`, `basement`, `library`, and `cafe`. Because of this, the API logic had to reflect the actual database schema instead of my first assumption about geographic cities. This made the backend more consistent with the data model.

If I had more time, I would evaluate performance more formally using Lighthouse and compare results across key pages such as the homepage, Browse page, and Room Detail page. The current prototype uses generated images and dynamic DOM rendering, so image compression and lazy loading would be realistic improvements. I would also add clearer loading and empty states for the location API, so users understand what is happening if detection fails or if no local rooms are found. Overall, the prototype performs reliably enough for a class project, but the development process showed me that stable technical behaviour depends on testing interaction flows, not only checking whether each page loads.

## Evaluation of User Experience and Accessibility

The final user experience is much clearer than the early version because users now have several connected ways to move through the application. A user can start from the homepage, explore the rotating room carousel, scroll through recommendation rows, click into a room detail page, or use “View all” links to open filtered Browse results. The Discover page also supports this flow by linking real tags to Browse filters. This made the application feel more like a connected product rather than a group of unrelated pages.

The Browse page was one of the biggest UX improvements. Earlier in development, the tags felt confusing because they were mixed together without a clear structure. A user could see many tags, but it was not obvious whether a tag described a genre, a mood, or a location. I redesigned the filters into three separate categories: genre, mood, and location. This made the interface easier to understand because users can filter based on intention. For example, if they are looking for an atmosphere, they can use mood; if they are looking for a music style, they can use genre; and if they want a place-based room, they can use location. I also made the homepage recommendation links pass real query parameters, such as `/browse?mood=chill` and `/browse?genre=indie`, so users do not lose context when they move from homepage recommendations into Browse.

The room detail page also improved the clarity of the “Sound Room” concept. Before adding this page, clicking “Enter Room” did not really feel like entering a room; it mostly sent users back to browsing. In the final version, each room has its own `/rooms/:id` page with a large rotating record image on the left, room information and a player-style section on the right, and comments below. This makes the room feel like a destination rather than only a card. It also supports the community goal of the app because users can read posts and comments and submit their own comment. This is still a prototype, but it better matches the original idea of music discovery happening inside shared spaces.

Accessibility testing changed several of my design decisions. I used WAVE to evaluate pages such as the homepage, Browse, Community, Profile, Discover, and Room Detail. One issue was that the homepage originally used large `div` elements for the visual title. It looked like a heading, but semantically the page did not have an `h1`, so WAVE reported a missing first-level heading. I changed the hero title into an actual `h1` while keeping the more experimental layout of “DISCOVER”, “SOUND”, and “ROOMS”. This showed me that visual hierarchy and semantic hierarchy are not the same.

WAVE also identified missing form labels. The Community page post input and the Room Detail comment textarea originally relied on placeholder text. I learned that placeholders are not proper labels because they disappear when users type and may not communicate the purpose of the field to screen readers. I fixed this by adding labels, including visually hidden `.sr-only` labels where I did not want visible text to change the layout. This was a small code change, but it made the forms more inclusive.

Colour contrast was another repeated accessibility issue. Many small metadata elements used light grey text, such as `#777`, on white or off-white backgrounds. WAVE marked several of these as low contrast, including post room labels, post actions, profile activity times, playlist numbers, and discover card metadata. I adjusted these colours to darker values such as `#222` or `#111` and sometimes increased font weight. I also learned that using opacity to make text look subtle can cause contrast problems. For example, the homepage subtitle originally used low opacity, which made it fail contrast checks. Replacing opacity with a darker colour value kept the visual style while improving readability.

There are still some UX issues I would improve. The Browse cards contain a lot of information, including image, title, description, tags, statistics, metadata, and an enter link. Although I adjusted card height and text clamping, the cards can still feel dense. In a future version, I would simplify the Browse cards and leave more detailed information for the Room Detail page. I would also test keyboard navigation and screen reader behaviour more thoroughly. WAVE was useful for identifying issues, but it cannot replace testing how real users move through the site.

## Critical Reflection and Improvement Planning

One major reflection from this project is that the scope was larger than it seemed during planning. “An indie music community platform” sounds clear as a concept, but once I started building, every visual feature required supporting logic. The carousel required database queries, JavaScript state, image paths, and navigation links. The Browse page required a tag system, query parameters, SQL conditions, and selected filter states. The comment function required route handling, form submission, user identity, posts, and comment relationships. This taught me that web features should be scoped according to the technical systems they require, not only according to how simple they look in a mock-up.

Another lesson was the importance of code organisation. As the project grew, the CSS became difficult to maintain because styles for the header, homepage, About, Browse, Community, Profile, Discover, and Room Detail pages were all in one large file. I reorganised the stylesheet into clearer sections for shared components and page-specific styles. This improved maintainability because I could find and edit styles more quickly. It also made the project feel more professional, since layout rules, reusable classes, and page-specific rules had a clearer separation.

Accessibility should also have been considered earlier. Many WAVE issues appeared late in development because I focused first on visual style and then checked accessibility afterwards. If I worked on this project again, I would define accessible design rules earlier, such as minimum contrast colours for metadata, consistent label patterns for forms, and semantic heading structure for each page. This would reduce the need for late-stage fixes and make the interface stronger from the start.

If I continued the project, my improvement plan would focus on making fewer features more complete. The first priority would be to make the community system fully dynamic, so users can create posts, reply to specific rooms, and manage their own comments. The second priority would be to make the player functional rather than only visual. The third priority would be performance and accessibility testing, including Lighthouse audits, lazy loading for images, keyboard navigation, and screen reader testing. These improvements are realistic because they build on the current structure instead of replacing it.

## Retrospective Assessment of Functional Requirements

My original functional requirements were mostly centred on discovery, browsing, user identity, and community interaction. The final prototype met the core requirements, but not always at the same level of completeness. The requirement for users to discover sound rooms was achieved through the homepage carousel, recommendation rows, and Discover page. The requirement for users to browse and filter rooms was achieved through the Browse page with genre, mood, and location filters. The requirement for users to view detailed room information was achieved through the Room Detail page. The profile requirement was also partly achieved because the logged-in user name appears in the header and profile page.

The community interaction requirement was only partially achieved. Users can submit a comment on a room detail page, but the Community page itself is still mostly static. The audio player is also a visual prototype rather than a working music player. These limitations show that some of my initial requirements were too broad for the time available. In planning, “community interaction” sounded like one requirement, but in implementation it involved database relationships, routing, user identity, form handling, validation, and feedback. This made me realise that future requirements should be prioritised more carefully.

Overall, I think the final prototype successfully demonstrates the main concept of Shen_ren.indie.music. It connects database content, filters, navigation, room detail pages, user identity, and basic commenting into one coherent system. It is not a production-ready application, but it shows a working foundation for a room-based indie music community. Most importantly, the project taught me that evaluation is not just the final step. Many of the strongest improvements came from testing the application, discovering problems, and then changing the design or code based on evidence.
