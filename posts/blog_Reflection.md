When I look back at this project, I feel that **Shen_ren.indie.music** changed a lot from my original plan. At the beginning, I imagined it more like a simple indie music community website: a homepage, a browse page, a profile page, and maybe some static community content. However, during development it gradually became a more connected web application. The final prototype has a dynamic homepage, a database-driven Browse page, location-based recommendations, user login display, profile and community pages, individual room detail pages, and a basic comment function. It is still a prototype, but compared with the early concept, it feels much closer to a real system.

The main concept of the application is “Sound Rooms”. Instead of treating music discovery as only playlists or tracks, the app presents music as rooms that users can enter, browse, and discuss. This idea shaped most of the design decisions. On the homepage, I wanted users to feel that they were discovering rooms visually, not just reading a list. That is why I built the rotating record-style carousel. Each room is represented by a circular image, and the selected room shows its title, tags, member count, comment count, and an “Enter Room” button. This part was one of the most successful parts visually, because it immediately communicates the music theme of the project. At the same time, it also created several technical problems that I did not expect.

One issue was that the carousel depended heavily on the data coming from the database. Earlier in the project, my JavaScript was still using old field names such as `name` or `online`, while my database query returned fields such as `title`, `member_count`, `comment_count`, and `cover_image`. Because of that, some parts of the interface showed `undefined`. This was a useful mistake because it made me understand that a dynamic interface is not just about writing JavaScript animation. The frontend and backend have to agree on the same data structure. Once I mapped the database fields properly, the carousel became much more stable.

Another problem happened when I clicked the left or right arrow in the carousel. At first, the room information box was visible on page load, but after switching rooms it disappeared. This happened because the script had been loaded more than once and because the animation class could remain active if the render process failed. I fixed this by only loading `soundroom-carousel.js` once, adding checks for missing elements such as `roomCounter`, and making the transition logic safer. This made me realise that performance and technical behaviour are not only about speed. A page can load quickly, but if an interaction breaks after one click, the system still performs badly from the user’s point of view.

The database became more important than I originally expected. In the final version, the homepage recommendation rows are not hard-coded. They pull rooms by real tags such as `chill`, `late-night`, `indie`, and `sydney`. The Browse page also filters rooms by genre, mood, and location. This was a strong part of the final prototype because the same database supports several different pages. It also made the system easier to maintain. If I add or change room data in the seed file, it can affect the homepage, Browse page, and room detail pages at the same time.

However, using a database also made small inconsistencies more visible. For example, I wanted the homepage to detect the user’s location and show local rooms. At first, the detected location was Waterloo, but the database did not have a `waterloo` tag; it had `sydney`. This caused the local recommendation row to show no rooms. I then changed the logic so suburbs like Waterloo, Redfern, Mascot, or Newtown are normalised to Sydney. Later, I realised the location tags in the database were not only Australian cities. They also included places like `berlin`, `hong-kong`, `tokyo`, `new-york`, and more conceptual locations such as `bedroom`, `studio`, `basement`, `library`, and `cafe`. Because of this, the API had to match the actual tag system instead of only handling a few city names. This was a good example of how technical logic should follow the data model, not just the developer’s first assumption.

In terms of user experience, I think the final prototype became much clearer than the early version. The user can start from the homepage, explore the hero carousel, scroll through recommendation rows, click into a room, browse by filters, or enter from the Discover page tags. This gives the application several connected pathways. The Browse page was especially important because it gives users more control. Earlier, all tags were mixed together, which made the interface confusing. I separated the filters into genre, mood, and location, which made the system easier to understand. A user can now search by title or description, or filter by a specific type of tag.

The room detail page also improved the user experience a lot. Before adding it, clicking “Enter Room” only sent users back to Browse or searched for the room title. That did not really feel like entering a room. Now each room has its own detail page with a large rotating record image, room information, tags, statistics, a player-style section, recent posts, recent comments, and a comment form. This makes the “room” concept feel more complete. It also supports the community goal of the app, because users are no longer just looking at rooms from outside; they can actually enter and participate.

Accessibility evaluation changed how I looked at my own design. I used WAVE to check the homepage, Browse, Community, Profile, Discover, and Room Detail pages. Some issues were easy to fix, but they showed me that visual design and semantic structure are different things. For example, the homepage originally had “DISCOVER” and “SOUND ROOMS” as large `div` elements. Visually they looked like headings, but WAVE reported that the page had no first-level heading. I changed the hero title into an actual `h1`, while keeping the experimental visual layout. This helped the page make more sense for assistive technologies without losing the design direction.

WAVE also found missing form labels. On the Community page, the post input only had placeholder text, and on the Room Detail page, the comment textarea also only had a placeholder. I learned that placeholders are not proper labels because they disappear when the user starts typing and may not be read clearly by screen readers. I fixed this by adding proper labels, including visually hidden labels using an `.sr-only` class. This was a small code change, but it made the form structure much more accessible.

Colour contrast was another issue. My interface uses a lot of black, white, and grey, but some grey text was too light, especially small metadata like post time, member counts, activity labels, and card labels. WAVE marked many of these as low contrast. I changed several colours from `#777` to darker values such as `#222` or `#111`, and sometimes increased font weight. This improved readability while still keeping the black-and-white visual style. I also learned that using opacity to make text look subtle can create accessibility problems. For example, the homepage subtitle had low contrast because I used `opacity: 0.4`. It was better to use a specific darker colour instead.

There were still some usability problems that I would improve if I had more time. The Browse cards contain a lot of information: image, title, description, tags, statistics, metadata, and an enter button. I adjusted the card height and text clamping, but the layout still feels dense. In a future version, I would simplify Browse cards and move more detailed information to the room detail page. I also think the Community page is still too static. It looks like a real feed, but it does not yet connect to database posts in the same way the room detail page does. A more complete version should allow users to create posts, open threads, and reply to specific discussions.

Looking at the functional requirements, I think the final prototype met the main goals but not every possible feature. The original goal was to create an indie music community hub where users could discover rooms, browse content, view profiles, and interact with music-related discussions. The final prototype does include these core areas. The homepage, Browse page, Profile page, Community page, Discover page, and Room Detail page all support the idea of a room-based music platform. The database also includes rooms, tags, memberships, posts, and comments, which gives the system a stronger technical base.

Some features were simplified or rescoped. The audio player on the room detail page is only a visual prototype, not a real music player. The comment function works at a basic level, but it does not yet support editing, deleting, moderation, or threaded replies. User accounts are also still prototype-style test users rather than a full authentication system. These limitations show that my original plan was ambitious. I could build the structure and interaction flow, but a production-ready community platform would need much more backend logic and user management.

The biggest lesson I learned is that a web application needs to be evaluated as a system, not just as a visual design. Earlier in the project, I focused mostly on how the pages looked. Later, I had to think about routing, database fields, JavaScript state, error handling, accessibility, and how one page connects to another. I also learned the importance of organisation. At one point, the CSS became difficult to manage because it included styles for the header, homepage, Browse, Community, Profile, Discover, About, and Room Detail pages all together. Reorganising the CSS into page-based and shared sections made the project easier to maintain and made the code feel more professional.

If I continued development, I would focus on three main improvements. First, I would make the community features fully dynamic, so posts and replies are created from real user actions and stored clearly in the database. Second, I would improve performance by compressing images, adding lazy loading, and running more formal Lighthouse tests. Third, I would continue accessibility testing beyond WAVE, including keyboard navigation and screen reader testing. WAVE helped identify many issues, but it does not replace real user testing.

Overall, I think Shen_ren.indie.music successfully communicates the idea of a room-based indie music community. It is not a finished product, but it demonstrates a working connection between database content, filtering, room navigation, user identity, and community interaction. More importantly, the process taught me that evaluation is not something that only happens at the end. Many of the best improvements came from testing the application, finding problems, and then changing the design or code based on what actually happened.
